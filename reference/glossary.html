Boot vocabulary without fog

Short definitions for terms used precisely throughout the course. Definitions will deepen as the implementation exposes more machinery.

Core terms

Application

The firmware that provides the device's intended behavior after the boot process selects and enters it.

BOOTSEL

An RP-series ROM boot mode selected on Pico 2 W by preventing normal external-flash boot, commonly by holding the board's BOOTSEL button during USB connection.

Boot chain

The ordered transfer of control through reset hardware, Boot ROM, a custom loader if present, startup runtime, and application.

Boot ROM

Raspberry Pi's immutable code in RP2350 mask ROM. It is the first software executed after reset and is distinct from your custom bootloader.

Bootloader

Software that discovers, validates, selects, loads, updates, or transfers control to another firmware image. In this course, “custom bootloader” means replaceable code in external flash.

CPU core

The programmable execution engine that fetches and performs instructions. RP2350 can expose Arm Cortex-M33 or Hazard3 RISC-V processors; the course begins with Cortex-M33 core 0.

External flash

Non-volatile storage outside the RP2350 package. Pico 2 W wires a 4 MiB serial NOR flash to the RP2350 for firmware and persistent data.

Firmware image

A structured collection of executable code, data, and metadata intended to be discovered or installed as one bootable unit.

Handoff

The controlled transfer from one boot stage to the next, including any required execution-state cleanup and destination setup.

Mask ROM

Memory whose contents are fixed as part of silicon manufacture. Normal software cannot erase or rewrite it.

Non-volatile

Retains stored information after power is removed. Mask ROM and flash are non-volatile; SRAM is not.

Power-on reset (POR)

A hardware reset that holds the chip inactive until its internal supply is high enough for reliable core operation, then begins the reset-release sequence.

Reset

A hardware transition that places selected chip state into defined conditions and restarts execution through the platform's reset path. Reset does not necessarily erase memory.

Reset handler

The entry routine for an executable image after the processor's reset/vector mechanism selects it. It normally prepares the language runtime before calling main().

SRAM

Fast, volatile read/write memory used for stacks, writable data, temporary work, and sometimes executable routines while flash is unavailable.

Startup runtime

The instructions between image entry and main() that establish memory and language invariants such as initialized data, zeroed BSS, and C++ constructors.

UF2

A block-oriented firmware transport format designed for drag-and-drop flashing. A UF2 packages addressable payload data; it is not the same thing as an ELF executable.

USB mass-storage mode

The host-visible drive interface offered by ROM BOOTSEL so a UF2 can be copied onto the device without an application or external debugger.

Vector table

An address table used by Cortex-M exception handling. Its first entries establish initial execution state, and later entries identify exception and interrupt handlers.

Volatile memory

Storage whose contents are not guaranteed after loss of power. This “volatile” is a hardware property and is distinct from the C++ volatile qualifier.

XIP

Execute in place: fetching instructions through the memory system from external serial flash without first copying the entire program into SRAM.

Distinctions worth protecting

Do not confuseWhy
Boot ROM vs custom bootloaderOne is immutable silicon-provided code; the other is your replaceable flash-resident firmware.
Reset vs power cycleSeveral reset sources exist, and different state can survive different reset depths.
Flash vs ROMBoth retain data without power, but flash is electrically erasable and ROM is not.
Firmware image vs UF2The image is the bootable content; UF2 is one container used to transport addressed blocks.
Hardware volatility vs C++ volatileOne describes retention across power loss; the other constrains compiler treatment of accesses.
