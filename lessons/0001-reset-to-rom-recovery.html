The first trustworthy boot model

Hardware events come before software instructions

When USB power reaches the board, the CPU cannot safely execute instructions immediately. Internal supply rails must become valid, reset logic must hold the chip in a defined state, and essential blocks must be released in an ordered sequence. The RP2350 datasheet calls the initial voltage-qualified reset a power-on reset and describes the ordered release using the Power-on State Machine.

That distinction matters: reset is not a C++ function. Reset is hardware behavior that establishes conditions under which a processor can begin its architecturally defined reset path.

The RP2350 contains 32 KiB of mask ROM. Raspberry Pi's Boot ROM image occupies this immutable memory and contains the first software instructions executed at reset. That is a concrete silicon fact, not a convention chosen by your CMake project. See RP2350 Datasheet, Chapter 5 and §5.1.

What the Boot ROM is responsible for

At this level, treat Boot ROM as a small trusted platform program. It examines boot conditions, prepares hardware needed for boot, decides whether recovery was requested, discovers an acceptable firmware image, and enters it according to the image metadata and device policy.

The exact RP2350 algorithm is richer than this first diagram. Later lessons will add OTP policy, secure and non-secure state, block loops, image definitions, partition tables, A/B slots, architecture selection, watchdog requests, RAM images, and other branches. The simple model is useful because it preserves the ordering without pretending the missing branches do not exist.

Model boundary: do not turn the diagram into a hand-written application jump yet. RP2350 image entry follows RP2350 metadata and Boot ROM rules. Generic STM32 or RP2040 examples are not evidence for the correct RP2350 handoff.

Why main() is late

The Cortex-M33 has no C++ symbol table searcher that looks for a function called main. A compiled image contains machine instructions at linker-selected addresses. Its entry/startup code establishes the language runtime and eventually performs an ordinary machine-level call or branch to the address associated with main.

Where your custom bootloader will fit

immutable RP2350 Boot ROM
            ↓
replaceable custom bootloader in external flash
            ↓
validated, separately linked application in external flash
            ↓
application startup and main()

Your custom bootloader does not replace the mask ROM. It is another bootable image discovered and entered by the ROM, and it later selects or enters an application. This distinction is the foundation of both recovery and secure-boot reasoning.

ROM, flash, and SRAM are not interchangeable

Two meanings of “volatile”

SRAM is volatile memory because it does not retain data without power. C++ volatile is a language qualifier that affects how the compiler emits accesses to an object. It does not make SRAM non-volatile, provide atomicity, fix races, or preserve values through reset.

Why external flash can hold executing code

Pico 2 W firmware usually executes through an execute-in-place mapping. The CPU issues an instruction fetch to an address in its memory map; the RP2350's cache and QMI hardware obtain the corresponding bytes from serial flash. The processor sees a memory address, while the memory system translates that access into communication with the external device.

That convenient abstraction creates a later bootloader problem: code cannot casually keep fetching from the same flash device while an erase or program operation makes it unavailable. Week 15 will derive the required SRAM execution and flash-safety rules.

What BOOTSEL changes

The Pico 2 W schematic labels BOOTSEL as disabling flash boot and forcing USB boot. Holding the button while applying USB power causes the Boot ROM to take its recovery path instead of relying on the normal flash image. See the official Pico 2 W schematic.

The resulting USB mass-storage interface is provided by code rooted in immutable ROM. Raspberry Pi's board documentation therefore states that BOOTSEL cannot be overwritten by ordinary software and remains a recovery path even when external flash is invalid. See Reset flash memory.

Day 1 · 1.5–2 hours

Derive the chain before memorizing labels

Exercise 1 — Predict from constraints

Answer without reopening the explanation above. Write one or two sentences for each.

  1. If external flash can be erased, why must the first recovery code live somewhere else?
  2. If SRAM loses state without power, why can it not be the permanent home of the application?
  3. If the CPU understands instructions rather than C++ function names, what must connect image entry to main?
  4. If a custom loader is replaceable, what must execute before it?
  5. If BOOTSEL bypasses normal flash boot, what failure class does it help recover from?
Check the reasoning after writing your answers
  1. Recovery must not depend solely on the storage it may need to repair. RP2350 places recovery-capable boot code in immutable mask ROM.
  2. SRAM is working storage, not power-independent firmware storage. Flash retains the image; startup reconstructs required SRAM state.
  3. Image metadata, vector/start information, startup instructions, and linker-selected addresses connect machine reset entry to main.
  4. The silicon-provided Boot ROM runs first and decides how to enter the flash-resident custom loader.
  5. It recovers from absent, invalid, or malfunctioning flash firmware by taking a ROM-provided USB path.

Exercise 2 — Draw three versions

On paper or in a plain-text file, draw these without copying the diagrams:

  1. The normal current path: ROM → existing flash image.
  2. The recovery path: reset → ROM → BOOTSEL USB.
  3. The future course path: ROM → custom loader → application.

For every box, annotate:

  • the storage holding its instructions;
  • whether that storage is writable;
  • who decides the next stage;
  • what evidence could show the stage ran.
Do not draw “power → main.” If your diagram omits reset hardware, Boot ROM, and startup, it hides exactly the architecture this course exists to reveal.

Day 2 · 1.5–2 hours

Diagnostic: find the real starting point

This is a baseline, not a performance test. Answer all twelve from memory, record your first score, and only then study the revealed explanations. Avoid viewing the page source before finishing.

1. Which software instructions run first after RP2350 reset?

The RP2350 Boot ROM is etched into 32 KiB of mask ROM and contains the first software executed at reset. External flash is considered later by that code.
2. What is the best first model of reset?

Reset places selected hardware state into defined conditions and restarts the platform's boot path. Different reset sources can affect different state; reset is not synonymous with erasing storage.
3. How do mask ROM and flash differ?

Both retain data without power, but ordinary firmware can erase and program flash under hardware rules. Mask ROM contents are physically fixed during chip production.
4. What is SRAM's initial role in this model?

SRAM is fast read/write working memory used for stacks, writable objects, buffers, and selected executable routines. Its contents are not retained through complete power loss.
5. What does holding BOOTSEL request?

The board button prevents the normal flash boot condition and causes the immutable Boot ROM to prepare its USB BOOTSEL services.
6. How is main() normally reached?

The linker places code and creates address relationships. At runtime, startup machine instructions establish required memory and language state before transferring control to main.
7. Where does this course's custom bootloader run?

The custom loader is a replaceable flash-resident stage. RP2350 Boot ROM remains the immutable first software stage and enters the loader according to image rules.
8. What does C++ volatile provide?

The qualifier makes accesses observable to the abstract machine in ways important for MMIO, but it is not a lock, atomic operation, memory barrier, or persistence mechanism.
9. What is a Cortex-M vector table for?

The Cortex-M vector table participates in reset/exception entry. Its first entries establish initial execution state, while later entries identify handlers for exceptions and interrupts.
10. What can happen when normal flash boot fails?

The Boot ROM validates boot structures according to its algorithm. When it cannot find an acceptable boot path, ROM recovery remains available rather than depending on the invalid application.
11. What does execute in place mean here?

XIP lets instruction fetches pass through the RP2350 memory/cache/QMI path to external serial flash, presenting it to software through mapped addresses.
12. What host observation supports BOOTSEL entry?

In ROM BOOTSEL, the host enumerates Raspberry Pi USB recovery interfaces and ordinarily mounts a volume labelled RP2350 for UF2 transfer.

Interpret the baseline

  • 10–12: the vocabulary is fluent; Week 1 should focus on causal explanations and evidence.
  • 7–9: the core model exists but contains gaps worth repairing before toolchain work.
  • 0–6: spend extra time redrawing the chain and comparing the three memory types. This is useful calibration, not failure.

Write down every answer you guessed correctly. A correct guess indicates fluency in the moment, not yet storage strength.

Day 3 · 1.5–2 hours

Verify the model against primary sources

Datasheet reading is a navigation skill. Your goal is not to absorb 1,380 pages. Your goal is to locate claims, identify the authority behind them, and distinguish what the document states from what you inferred.

Reading 1 — The immutable first program

Open RP2350 Datasheet, Chapter 5 introduction and §5.1.

  1. Find the stated mask ROM capacity.
  2. Find the statement identifying Boot ROM as the first reset-time software.
  3. Scan the list of concepts in §5.1 without trying to learn them yet.
  4. Write why “Boot ROM source is public” does not mean “Boot ROM is writable.”

Reading 2 — Where BOOTSEL branches

Open the Boot ROM boot-path description around RP2350 Datasheet, §5.2 boot path. Locate the decision that checks a BOOTSEL request before normal flash boot proceeds.

Record three distinct ways the Boot ROM can learn that BOOTSEL was requested. Do not worry about configuring all of them; the board button is the one used this week.

Reading 3 — Board wiring, not chip theory

Open the Pico 2 W schematic. Find:

  • the BOOTSEL label and its stated effect;
  • the 32 Mbit/4 MiB flash device;
  • the wireless-interface GPIO note;
  • the LED's relationship to the wireless device.

This is an important method: use the RP2350 datasheet for silicon behavior and the Pico 2 W schematic for how the board connects that silicon.

Day 4 · about 2 hours

Hardware lab: observe immutable recovery

This lab does not erase or program flash. Do not copy any UF2 onto the mounted volume yet. If the host offers to format the device, cancel that prompt.

What you are testing

Hypothesis: holding BOOTSEL while applying USB power selects a host-visible recovery mode supplied independently of the current flash application.

Independent variable: whether BOOTSEL is held at connection.

Evidence: USB enumeration and the presence of an RP2350 mass-storage volume.

Step 1 — Establish the host baseline

Unplug the Pico 2 W. Run:

lsusb
lsblk -o NAME,LABEL,SIZE,TYPE,TRAN,MOUNTPOINTS

Save or copy the output. You need a “before” observation so that a later device entry is evidence rather than assumption.

Step 2 — Force BOOTSEL

  1. Keep the board unplugged.
  2. Press and hold the physical BOOTSEL button.
  3. While holding it, connect the USB cable.
  4. Release the button after the cable is seated.

Now run the observations again:

lsusb
lsblk -o NAME,LABEL,SIZE,TYPE,TRAN,MOUNTPOINTS
findmnt -rn -o SOURCE,TARGET,LABEL | grep -i rp2350 || true

Expected evidence includes a newly enumerated Raspberry Pi device and a small removable volume labelled RP2350. Desktop automount behavior varies, so the volume may exist without being mounted.

Step 3 — Inspect without modifying

If lsblk shows a mount path, list it. Replace the placeholder with the exact path reported by your machine:

ls -la /exact/mount/path

# If this file exists, read it without changing anything:
sed -n '1,40p' /exact/mount/path/INFO_UF2.TXT

Record:

  • USB device description or identifier;
  • block-device name;
  • volume label;
  • mount path, if any;
  • files visible on the volume;
  • what changed relative to the unplugged baseline.

Step 4 — Compare normal connection

  1. Unplug the board.
  2. Wait several seconds so the host removes the USB device.
  3. Reconnect without touching BOOTSEL.
  4. Repeat lsusb and lsblk.

There are two useful outcomes:

  • The mass-storage volume disappears: a flash application or other normal boot path ran instead of BOOTSEL.
  • The mass-storage volume returns: flash may contain no bootable image, or another BOOTSEL request exists. The Boot ROM recovery path still worked; the normal flash outcome simply needs investigation in Week 2.

The controlled failure

Your controlled “failure” is connecting without BOOTSEL and predicting that ROM USB storage will not appear when a valid normal image runs. This comparison is intentionally non-destructive. Week 2 will introduce a known firmware image before we deliberately corrupt or erase anything.

Troubleshooting from evidence

ObservationLikely class of causeNext non-destructive check
No new USB deviceCable, port, power, button timing, or host USB issueTry another known data port/cable and repeat the unplugged baseline
USB device appears, no mounted volumeAutomount disabled or permissionsUse lsblk; a block device can exist without a mount
Volume appears during normal connection tooNo valid flash boot, persistent request, or BOOTSEL still activeEnsure the button is released and capture both USB descriptions
Host asks to formatHost did not recognize the exposed filesystem correctlyCancel; do not format; capture lsusb and lsblk

Explain what the lab did not prove

Seeing a USB volume proves that a recovery-capable path enumerated. It does not yet prove every Boot ROM branch, the contents of your flash, the validity of a custom image, or the exact machine instruction that executed first. Good engineering claims stay inside the evidence.

Day 5 · 1.5–2 hours

Teach the mechanism back

Close the glossary and diagrams. Speak or write a five-minute explanation for an experienced C++ developer who has never used a microcontroller.

Your explanation must answer

  1. What hardware event prevents the processor from starting too early?
  2. What memory contains the first software executed after reset?
  3. Why can that memory recover a broken external-flash application?
  4. What decision does BOOTSEL influence?
  5. What does external flash contribute to normal boot?
  6. What does SRAM contribute once an image begins?
  7. Why is main() not the image's first machine-level event?
  8. Where will the future custom loader sit?

Interleave the three paths

From memory, draw these in a random order:

  • normal flash application;
  • ROM BOOTSEL recovery;
  • future custom loader and application.

Mixing related paths prevents recognition from masquerading as recall.

One-minute distinctions

Explain each pair in one sentence:

  • reset vs power cycle;
  • Boot ROM vs custom bootloader;
  • mask ROM vs flash;
  • volatile SRAM vs C++ volatile;
  • firmware image vs UF2 container;
  • source-level main vs machine-level image entry.
Common misconceptions to check after the teach-back
  • “BOOTSEL is stored in the application.” It is a board-selected path handled by immutable Boot ROM.
  • “Reset erases RAM and flash.” Reset effects depend on the reset source; flash is not automatically erased.
  • “The CPU calls main after reset.” Startup instructions and image-entry rules exist between those events.
  • “The onboard LED is GP25.” On Pico 2 W, the visible LED is controlled through the CYW43439 wireless device.
  • “Public Boot ROM source makes ROM replaceable.” Published source aids understanding; the manufactured mask ROM remains immutable.
